# 需求准入契约（Requirement Gate）

工程规则见 `AGENTS.md §9`；填写示例见 `Docs/Requirements/需求模板_v1.docx`；空白卡见 `Docs/Requirements/_TEMPLATE.md`。

## 第一原则

**需求不完整，就不开始实现。** 缺字段时唯一正确的动作是提问，不是"先按理解做一版"。
把假设当正式需求执行，是这套流程里最严重的错误——它会把不确定的设计固化成代码。

## 收到需求后的固定动作

1. **判定级别**（写进卡片的「基本信息」，决定要写多细）：

   | 级别 | 什么时候用 | 必填内容 | 模板 |
   |---|---|---|---|
   | **L0 小细节** | 文案、UI 间距、单个数值、一行明确 bug | 功能 ID、改什么、验收（≥1 条）、影响面、待确认 | `_TEMPLATE_L0.md` |
   | **L1 功能改动** | 改一条规则、加按钮流程、加一个遗物 | §1 基本信息、§2 目的、§3 范围、§4 触发/处理/输出（≥1 条 `[MUST]`）、§9 验收（≥3 条）、§10 待确认 | `_TEMPLATE.md` 只填这几节 |
   | **L2 大功能** | 新系统、跨模块、改存档/经济 | 完整 10 节 + 8 项 + 边界 4 类 + 技术约束 | `_TEMPLATE.md` 全填 |

   判断标准：**新增一个系统，或改跨系统契约（事件协议、存档结构、经济循环、公共接口）→ L2**；
   现有系统内部加/改规则（哪怕顺带新增了 `Global` 状态、抛了新事件）→ **L1**；只改表现或数值 → L0。
   **实施复杂度不算级别**：改了几个文件、拆给几个角色，都不影响判定。
   **L0 的门槛是「验收能一句话说清」**，说不清就升 L1；L0 泛滥等于没写。

2. **写需求卡**：`Docs/Requirements/<ID>_<名称>.md`。
   ID 规则：`SYS-` 系统 / `GP-` 玩法 / `EX-` 执行表现 / `QA-` 测试。

3. **跑机器检查**（按级别校验，级别从卡片里读，也可用 `-Level` 强制）：

   ```powershell
   powershell -ExecutionPolicy Bypass -File Tools\Agent\requirement-check.ps1 -Path Docs\Requirements\SYS-002_商店刷新.md
   # 强制按某一级校验（例如怀疑卡片写得太薄）：
   powershell -ExecutionPolicy Bypass -File Tools\Agent\requirement-check.ps1 -Path ... -Level L2
   ```

   退出码 0 才允许继续；1 就把缺项清单原样返回给需求方。

4. **通过后**才拆团队任务（`team_task_create`，带验收标准和写范围）。

## 8 个必填项（L2 用；L0/L1 只取其中一部分）

| # | 内容 | 不合格的例子 |
|---|---|---|
| 1 | 功能 ID + 版本 + 状态 + 优先级 | 没 ID；状态写成"进行中" |
| 2 | 设计目的（体验目标与实现规则分开） | 只有"加个刷新按钮" |
| 3 | 功能范围（包含 / 不包含 / 前置） | 只写"包含"，不写"不包含" |
| 4 | 需求详情（触发/输入/处理/输出/状态/数值） | "随机生成"这种不可验证表述 |
| 5 | 边界与异常（≥4 类） | 只写"异常时提示" |
| 6 | 技术约束（依赖/不变量/禁改） | 不写依赖系统 |
| 7 | 验收标准（≥3 条可验证） | "体验良好" |
| 8 | 待确认问题（没有写「无」） | 整段留空 |

## 提问规范

- 一次最多问 **5 条**，按影响排序（先问会改变实现方向的）。
- 每条给出**建议默认值**，让对方可以直接回"按你说的"。
- 不把"我猜"写成需求；确实需要先推进时，在卡里写成 **「假设待确认」** 并保持 `状态: Draft`，
  且必须拿到对方一句明确同意才能实现。

## 需求强度标记

每条处理规则带标记：
- `[MUST]` 必须满足，不可自行更改
- `[MUST NOT]` 明确禁止
- `[MAY]` 可选实现

至少一条 `[MUST]` 或 `[MUST NOT]`；只有 `[MAY]` 等于没约束。

## 写需求的几条硬要求（来自规范原文）

- 区分**体验目标**与**实现规则**：体验目标写"减少挫败"，规则写"每阶段可刷新 1 次"。
- 用**可验证**的表达：写数量、范围、重置时机、去重范围，不写"适当""随机""不能重复"。
- **本次包含 / 本次不包含**分开写，防止实现方自行扩范围。
- 参考作品不自动成为规则：注明「可借鉴」与「不可照搬」的部分。
- 关键规则不能只存在于图片里，必须有文字。

## 交付时怎么报告

实现完成后按需求卡的验收标准逐条对照，区分：
**已实现 / 已验证（跑了什么）/ 未验证（为什么）/ 失败 / 待办**。
"写完代码"不等于"通过验收"。

## 需求完成后：归档（强制）

验收通过后必须写归档，否则该需求不算收尾：

- 路径：`Docs/Requirements/Archive/<ID>_<名称>.md`（从 `_TEMPLATE.md` 复制；**所有需求归档放同一目录**）。
- 四项必填，缺一项视为未归档：
  1. **改动名称**：需求卡链接 + 一句话概括；
  2. **改动时间**：开始 / 完成 / 参与角色；
  3. **改动内容**：实现了哪些 `[MUST]`、改了哪些文件（代码/资产/prefab/文档）、关键实现说明、验证结果；
  4. **后续需要增加和注意的点**：待补功能、坑（改了会怎样）、可调数值与位置、相关文档。
- 归档要在**回复用户之前**写完，和代码同一次提交；不要事后补。
- 归档里写的「坑」要从本次实际踩到的来（例如默认值陷阱、AB 必须重建、数据条数约束），不要写通用套话。
