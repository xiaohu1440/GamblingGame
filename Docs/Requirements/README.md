# 需求文档（Requirements）

这里存放**可执行的需求卡**。规则依据《AI 游戏策划案编写与协作规范》v1.0。

## 目录

```
Docs/Requirements/
  _TEMPLATE.md              # L1/L2 卡片模板
  _TEMPLATE_L0.md           # L0 简略卡模板（小改动用）
  SYS-002_商店刷新.md        # L1 已填示例
  SYS-001_彩蛋保底.md        # L2 已填示例
  需求模板_v1.docx           # 给主策划看的完整模板 + 填写示例（Word）
  需求管理表_v1.xlsx         # 需求总表（策划/程序/美术 + 每日需求 + 汇总）
  Archive/                  # 需求归档：验收通过后写，所有归档放这一处
    _TEMPLATE.md            # 归档模板（四项必填）
    SYS-001_彩蛋保底.md      # 已归档示例
  README.md
```

> `需求管理表_v1.xlsx` 是需求的**总索引**：一条需求在对应角色页占一行，状态和完成后的反馈都在表里；
> 每日收尾用「每日需求」页做复盘（是否完成 / 是否需要修改 / 是否需要删除）。

ID 前缀：`SYS-` 系统、`GP-` 玩法、`EX-` 执行表现、`QA-` 测试。
命名：`<ID>_<名称>.md`，例如 `GP-004_遗物选择.md`。

## 分级（先定级别，再决定写多细）

级别写在第 1 节「基本信息」里，检查脚本按它校验；未写按 L2（最严）处理。

| 级别 | 什么时候用 | 必填 | 模板 |
|---|---|---|---|
| **L0 小细节** | 文案 / UI 间距 / 单个数值 / 一行明确 bug | 功能 ID、改什么、验收 ≥1 条、影响面、待确认 | `_TEMPLATE_L0.md` |
| **L1 功能改动** | 改一条规则 / 加按钮流程 / 加一个遗物 | §1 基本信息、§2 目的、§3 范围、§4 触发·处理·输出（≥1 条 `[MUST]`）、§9 验收 ≥3 条、§10 待确认 | `_TEMPLATE.md` 只填这几节 |
| **L2 大功能** | 新系统 / 跨模块 / 改存档·经济 | 完整 10 节 + 下面 8 项 + 边界 4 类 + 技术约束 | `_TEMPLATE.md` 全填 |

判断标准：**新增一个系统，或改跨系统契约（事件协议、存档结构、经济循环、公共接口）→ L2**；
现有系统内部加/改规则（哪怕顺带新增了 `Global` 状态、抛了新事件）→ **L1**；只改表现或数值 → L0。
**实施复杂度不算级别**：改了几个文件、拆给几个角色，都不影响判定。
**L0 的门槛是「验收能一句话说清」**，说不清就升 L1。

## 准入规则（L2 的 8 个必填项）

L2 需求在开始实现前必须包含以下 8 项，缺一项就不得开工，只能先提问（L0/L1 只取其中一部分）：

1. 功能 ID + 版本 + 状态（Draft/Review/Approved）+ 优先级
2. 设计目的（体验目标与实现规则分开）
3. 功能范围（本次包含 / 本次不包含 / 前置条件）
4. 需求详情（触发条件 / 输入 / 处理规则 / 输出 / 状态变化 / 数值与公式）
5. 边界与异常（无效输入 / 资源不足 / 重复触发 / 中途退出 至少 4 类）
6. 数据与技术约束（依赖系统 / 必须保持的不变量 / 禁止修改的内容）
7. 验收标准（≥ 3 条可验证的勾选项）
8. 参考与待确认事项（没有就写「无」）

## 机器检查

```powershell
# 级别从卡片里读
powershell -ExecutionPolicy Bypass -File Tools\Agent\requirement-check.ps1 -Path Docs\Requirements\SYS-002_商店刷新.md

# 怀疑卡片写得太薄时，强制按更高级别校验
powershell -ExecutionPolicy Bypass -File Tools\Agent\requirement-check.ps1 -Path Docs\Requirements\SYS-002_商店刷新.md -Level L2
```

- 退出码 `0`：满足该级别要求，可以拆任务、开始实现。
- 退出码 `1`：打印全部缺项，把清单发回需求方补齐。

## 分级

| 级别 | 典型需求 | 要求 |
|---|---|---|
| L0 小细节 | 改文案 / UI 间距 / 单个数值 / 一行 bug | 功能 ID、改什么、验收 ≥1、影响面、待确认 |
| L1 功能改动 | 改一条规则 / 加按钮流程 / 加一个遗物 | §1、§2、§3、§4（≥1 条 MUST）、§9（≥3 条）、§10 |
| L2 大功能 | 新系统 / 跨模块 / 改存档·经济 | 完整 10 节 + 8 项 + 边界 4 类 + 技术约束 |

## 归档（验收后必做）

需求验收通过后，在 `Docs/Requirements/Archive/<ID>_<名称>.md` 写归档（模板 `Archive/_TEMPLATE.md`），四项必填：

1. **改动名称**（需求卡链接 + 一句话）
2. **改动时间**（开始 / 完成 / 参与角色）
3. **改动内容**（实现了哪些 `[MUST]`、改了哪些文件、关键实现、验证结果）
4. **后续需要增加和注意的点**（待补功能、坑、可调数值与位置、相关文档）

归档与代码同一次提交；没有归档的需求视为未收尾。示例：`Archive/SYS-001_彩蛋保底.md`。

## 和团队分工的衔接

需求卡通过检查后，Lead 才把它拆成 `team_task_create` 任务（带验收标准和写范围），
派给程序 / 美术 / 执行策划。验收标准逐条对应任务完成条件，实现方不得自行扩大范围。
